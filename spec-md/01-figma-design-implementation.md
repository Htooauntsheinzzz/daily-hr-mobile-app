# DailyHR mobile design implementation plan

Build the employee and HR administrator experiences in Flutter for iOS and Android. Start with the role-specific journeys below. Use the [complete frame and component index](02-figma-frame-index.md) to find every field state, picker, confirmation and result. [DailyHR design in Figma](https://www.figma.com/design/8JAJChwmBDUM2dkdvdXHgU/Daily-HR-Mobile-Programming?node-id=0-1)

## Use Figma MCP for each screen

1. Open the linked design through Figma MCP. Start a file session with file key `8JAJChwmBDUM2dkdvdXHgU`. Page 1 has node ID `0:1`. A URL ending in `node-id=18-303` refers to MCP node `18:303`.
2. Find the screen and its variants in the index. Use `get_metadata` for hierarchy and a scoped, read-only `use_figma` query for text, visible layers, component instances, layout, variables and prototype destinations. Check visibility and prototype conditions before treating overlapping labels as simultaneous content.
3. Use `get_screenshot` on the exact frame and its relevant overlay or feedback state. Match the rendered layout, assets, type, spacing, selected tab and control order. Use the component source when an instance inherits its appearance. Recheck the current file if the snapshot and the design differ.
4. Translate each family of frames to one data-driven screen with appropriate state. Keep time, employee identity, dates, amounts and status in shared feature data. Compare the resulting view with the same Figma node at its reference size before testing other device sizes.

## Implementation sequence

| Step | Screens and interaction | Completion check |
| --- | --- | --- |
| 1. Brand and shared controls | Use the app icon, both wordmarks, splash Start/Reveal/Rest, sign-in form, bottom navigation, icon set, directory row, balance card and calendar grid. Apply the [project palette](../Agent.md) through the Flutter theme. Use the existing image, icon and logo asset folders. | Splash resolves once. Reused fields, icons and navigation match their source instances. |
| 2. Access and account | Implement employee and HR sign-in, password visibility, loading, required fields, invalid email, incorrect credentials, offline and unassigned-role feedback. Restore the appropriate returning-user path. Each role can open its profile, cancel sign-out or confirm it. | Test fresh launch, restored session, a failed login followed by retry, and sign-out followed by system Back. |
| 3. Dashboards and navigation | Employee Home shows attendance, hours, recent leave/OT, quick actions and notifications. Employee tabs are Home, Attendance, Calendar and Profile. HR Overview shows daily totals, leave/OT queues and quick actions for employees, attendance, leave, OT and payroll. HR tabs are Overview, Employees, Attendance and Profile. Its account menu opens Profile or Sign out. | Open each quick action and return to the correct role and selected tab. Update dashboard summaries after decisions, attendance events and publication. |
| 4. People | Employee Profile opens Edit contact details (mobile number and personal email), then returns to the saved profile. HR Directory opens a record, Add employee or Edit employee. The form has full name, work email, mobile number, position and department. Implement required-field feedback, position/department pickers, saved results and deactivation confirmation. | Exercise both example employees. Changing only the department preserves the position and vice versa. Cancel preserves the original record. Confirming deactivation updates that employee’s detail and directory row. |
| 5. Attendance | Connect Ready, location prompt, location unavailable, Working, confirm checkout and Complete. Display check-in, check-out and working hours. The employee calendar selects a date and shows its record. HR daily review selects a date and drills into one employee. Use Bangkok local time for the displayed workday. | Dismiss checkout and verify the shift stays open. Finish checkout and verify the times and hours agree across employee home, calendar and HR daily review. Exercise the unavailable-location path. |
| 6. Leave | My leave contains balances and requests. New request collects leave type, start/end dates and reason. Keep entered fields when opening the type picker. Implement missing details, ready, pending, resolved and confirmation states. Employee may cancel a pending request. HR opens Leave review and confirms approval or rejection. | Submit two requests, resolve one and check that only its status changes across detail, list, dashboard and notifications. Resolved detail must show the decision and retire pending actions. |
| 7. Overtime | My overtime opens a request with work date, start, end, reason and calculated hours. Implement the four pickers/input states, validation and submission. HR opens the review queue, checks request detail and records a decision. Include the second request example from Paydesk. | Changing either time recalculates hours. A decision on one date updates that request. Only approved entries for the selected employee and pay period contribute to payroll. |
| 8. Payroll | HR selects a month and employee, opens pay settings, edits base salary, hourly OT rate, insurance and salary advance, and inspects approved overtime entries down to individual dates. Prepare, calculate, review the draft and publish. Support monthly registers, published detail and employee payslip history. Work frames cover calculation states. Paydesk frames show itemized employee and month drilldowns. | Derive overtime pay from included hours × rate and net pay from base + overtime pay − itemized deductions. Compare draft and published totals. Verify that the employee sees only their own published payslips and that opening October preserves November’s record. |
| 9. Notifications | Open Notifications from employee Home. Link a leave or overtime decision to its request and a publication to its payslip. Resolve the destination by record and month. | Follow two notifications of the same type and verify that each opens its own detail. Return to the notifications list. |

## Mobile acceptance checks

- [ ] Compare screenshots with Figma at the source frame size (the home, sign-in and prepare-payslip frames are 402 × 874). Repeat on a narrower Android emulator and an iOS simulator. Check safe areas, keyboard scrolling, text scaling and bottom navigation.
- [ ] Test empty, entered, invalid, loading, saved, pending, resolved and confirmation states wherever the index shows them. Back or Cancel must return to the correct record with the expected form state.
- [ ] Use fictional records for the design implementation. Keep role, employee, request and pay period consistent across navigation. Treat sample salaries and displayed totals as fixtures. Backend selection remains open in the [decision log](00-changes-and-decision.md).
- [ ] Run the checks in the [project README](../README.md). Record which flows and devices were exercised, along with any unresolved design differences.
